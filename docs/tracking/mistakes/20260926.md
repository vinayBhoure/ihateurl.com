### Clerk UserButton custom menu items built in a Server Component
- Error: runtime (dev server, `/app`) — console error "Clerk: `<UserProfile />` can only accept `<UserProfile.Page />` and `<UserProfile.Link />` as its children. Any other provided component will be ignored. Additionally, please ensure that the component is rendered in a client component." Surfaced as a "2 Issues" overlay on first load; the custom menu items ("My public page", "Settings") silently did not render — only Clerk's defaults showed.
- Cause: added `<UserButton.MenuItems>`/`<UserButton.Link>` (plan 6 C2.4) directly inside `app-header.tsx` and `public-header.tsx`, both Server Components. Clerk inspects the `type` of `UserButton`'s children to recognize `MenuItems`/`Link`/`Action`; that identity check does not survive the RSC-to-client serialization boundary, so children built in a Server Component are dropped even though `lint`/`tsc`/`build` all passed clean.
- Fix: extracted a `"use client"` component `src/components/user-menu.tsx` that renders `<UserButton>` with the custom `MenuItems` entirely inside it, taking only a plain `username?: string` prop; both headers now render `<UserMenu username={...} />` instead of building the Clerk children themselves (commit `3b2ac93`).
- Avoid: any Clerk component with custom sub-children (`UserButton.MenuItems`, `UserProfile.Page`, etc.) must be constructed inside a component that already has `"use client"` — never assemble it in a Server Component and pass it down, even as a prop/child. `lint`/`tsc`/`build` do not catch this; only running the page and opening the dev overlay (or the browser console) does.

### `prisma migrate dev` can't run in this non-interactive shell
- Error: build/migration — `npx prisma migrate dev --name require_unique_collection_public_id` (and `--create-only`, and piping `yes |` into it) all failed with "Prisma Migrate has detected that the environment is non-interactive, which is not supported," even though the schema change itself (making `Collection.publicId` `NOT NULL` + `@unique` after a clean backfill) was safe. `migrate dev`'s confirmation prompt for "this could cause data loss" warnings has no non-interactive override flag; only the first migration in this same session (a plain nullable-column add, no warning) had run fine.
- Cause: neither the Bash nor PowerShell tool in this environment attaches a real TTY, and `prisma migrate dev` hard-refuses any migration that would normally ask for a y/n confirmation when it can't detect an interactive terminal — there is no bypass flag for `migrate dev` itself (unlike `db push --accept-data-loss`).
- Fix: generated the exact same SQL Prisma would have written, via the read-only `prisma migrate diff --from-schema-datasource=./prisma/schema.prisma --to-schema-datamodel=./prisma/schema.prisma --script` (no interactivity, no DB writes); wrote that output verbatim into a new `prisma/migrations/<timestamp>_<name>/migration.sql` folder (Prisma's own naming convention); applied it with `prisma migrate deploy` (also non-interactive-safe); then `prisma generate` to refresh the client. Migration content is Prisma's own auto-generated SQL, not hand-written — satisfies `.claude/skills/prisma-change`'s "not hand-edited" rule in spirit even though the CLI subcommand differs from `migrate dev`.
- Avoid: for any schema change likely to trigger Prisma's data-loss confirmation (dropping a column, adding `NOT NULL`/`@unique` to a column that may hold nulls, etc.), expect `prisma migrate dev` to fail outright in this environment. Go straight to the `migrate diff --script` -> hand-place `migration.sql` -> `migrate deploy` -> `prisma generate` sequence instead of retrying `migrate dev` with different flags.

### Stale `.next/dev/types` broke `tsc`/`build` after deleting a route folder
- Error: build — after deleting `src/app/(public)/[username]/` (moved to `src/app/(public)/u/...`), both `npx tsc --noEmit` and `npm run build` failed on `.next/dev/types/validator.ts` and `.next/types/validator.ts`: `Cannot find module '../../../src/app/(public)/[username]/[slug]/page.js'`. `next build` alone did not regenerate `.next/dev/types` (that's the `next dev`-specific type cache from earlier sessions in this conversation) even though it did recompile everything else successfully.
- Cause: `.next/` is a build cache; `next build` doesn't fully clean stale entries left by a prior `next dev` run when a route file is deleted mid-session, and `tsconfig.json`'s `include` picks up both `.next/types/**` and `.next/dev/types/**`, so the stale reference fails type-checking even though the actual app code was already correct.
- Fix: `rm -rf .next` before rebuilding; `npm run build` then regenerated clean types and succeeded.
- Avoid: after deleting or moving any `src/app/**` route file, delete `.next/` before the next `tsc`/`build` run rather than trusting an incremental rebuild to catch up — this project's dev/build history in a long session makes stale route types easy to hit.
